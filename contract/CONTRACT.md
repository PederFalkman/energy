# Advisory governance contract — v1.1.0

Normative. Where this document and an implementation disagree, this document is
correct and the implementation has a defect.

The product is advisory. It does not submit bids, place orders, or determine
price, quantity or timing. Two findings shape everything below: **learned memory
is only admissible where a mechanical judge exists**, and **structure enforced by
construction beats structure encouraged by a penalty.**

---

## 1. The two structural guarantees

These are the reason the contract is owned centrally. They must hold
**identically** in every implementation, and they are not checks — they are
properties of each implementation's type system.

### 1.1 Forbidden recommendations are unconstructible

Scope × subject:

|  | `PHYSICAL_ASSET` | `EXCHANGE_TRADED` |
|---|---|---|
| `GENERIC` | constructible | constructible |
| `CLIENT_SPECIFIC` | constructible | **MUST NOT EXIST** |

A client-specific recommendation on a financial instrument is investment advice
under MiFID II Art. 4(1)(4), which Layer is not authorised to give.

**Conformance requirement.** An implementation MUST NOT provide a constructor,
factory, builder or deserialiser that yields an *instance* of the forbidden pair.
Adding the capability must require deleting or editing a type declaration, so it
cannot be gained by forgetting a policy.

**The cell SHOULD be occupied by a named uninhabited type, not left absent.**
This was amended in v1.1.0 after two independent implementations of this
contract disagreed, and the second one's reasoning was better: *a cell merely
missing from the table is indistinguishable from an oversight, and a later
contributor would "complete" it.* A named type — `InvestmentAdviceNotOffered` or
equivalent — whose constructor raises documents the refusal in the place someone
would look to add it, and enabling the capability then means **deleting a class**,
which shows up in a diff.

An uninhabited type is not the same as a call-time check, and the distinction
matters: the type has no instances *ever*, for any caller, so there is no code
path that yields one. A guard that could be reached with the right arguments
would not be conformant.

Two further requirements, so the uninhabited type does not become the only
control:

- The forbidden pair MUST NOT be reachable through any factory or type table
  that returns constructible types.
- An implementation MUST prevent a *new* type from claiming the forbidden pair —
  in a language with subclass hooks, by refusing such a declaration at
  class-definition time. Occupying the cell stops it being filled by omission;
  this stops it being filled by addition.

### 1.2 Numeric values never pass through a language model

A narrative generated by a language model receives **references**, never values.
Values are rendered by code afterwards, from the stored record.

**Outbound** (into the model). The type crossing the boundary MUST NOT be able to
carry a float, integer, decimal or complex at any depth, nor a string containing
a value: a decimal number, or a digit adjacent to a unit (`MW`, `MWh`, `EUR`,
`SEK`, `%`, `/MWh`). Booleans are permitted — a flag is a state, not a quantity.

**Inbound** (out of the model). Generated text MUST be refused if it contains
**any digit** outside a placeholder. This rule is deliberately stricter than the
outbound one. The risks differ: outbound the danger is a stored value leaking
into a prompt, inbound it is the model writing a figure from memory. A rule
targeting only decimals and units admits `the price was 41`, which is the
wrong-digit-in-a-price failure this guarantee exists to prevent.

**Stated limit.** A quantity written as a word ("roughly forty megawatts") is not
detectable, and no rule catching it would leave ordinary prose usable. The
guarantee is: no value read from the record reaches the model, and no digit the
model wrote reaches the reader.

## 2. Domain model

### `Decision`
Identifier; timezone-aware timestamp; the recommendation; a **reference** to the
input snapshot (id + content digest), never a copy; the physical feasibility
envelope in force at that moment; model version; code version; the data-rights
state of every input.

Append-only and immutable once written. A correction is a NEW record that
supersedes the old one; the original stays readable. Writing an existing id MUST
fail.

Copying observations into the record is a contract violation: it builds a second
corpus of licensed market data inside the audit trail.

### `Outcome`
The observable that settles a decision: source, observation or settlement
timestamp, value, provenance.

**Provenance MUST be `OBSERVED`, checked at construction.** A modelled or
interpolated value is not an outcome. Grading a decision against a number our own
model produced makes every lesson a confirmation of the model that produced it.

### `Judge`
A registry mapping each decision type to the mechanical outcome that grades it:
day-ahead outturn, imbalance settlement, realised curtailment, measured thermal
loading.

A decision type with no registered judge is **storable but UNJUDGEABLE**, and
MUST be marked so explicitly. An implementation MUST NOT nominate a nearby
observable to make a type scoreable. A judge whose publisher is the
implementation's own organisation is not mechanical and MUST be refused.

### `Lesson`
Derived from decision–outcome pairs. Carries the regime it was learned under, the
observation count behind it, and its admission record.

**A lesson can never set a parameter, relax a limit, or alter a
recommendation.** Conformance requires this be enforced by **absence of a write
path**, not by convention: the lesson type MUST carry no numeric field, so there
is nothing on it to assign to a calculation input. Observation count belongs on
the admission record, not the lesson body.

## 3. Admission gate

A lesson is admitted only if **all** hold. Rejection MUST name the failed
condition using the vocabulary in §3.1.

1. a registered mechanical judge produced the outcome
2. outcome provenance is `OBSERVED`
3. nothing opinion-shaped — no claim about direction, size, or what someone
   should do
4. nothing derived from chat, fetched web content, or model-generated text
5. no client, counterparty or person named or identifiable
6. concerns method or mechanics, not a market view

### 3.1 Rejection reasons (closed set)

`NO_REGISTERED_JUDGE` · `OUTCOME_NOT_OBSERVED` · `OPINION_SHAPED` ·
`UNTRUSTED_DERIVATION` · `NAMES_A_PARTY` · `MARKET_VIEW` · `NO_EVIDENCE` ·
`ROLE_NOT_PERMITTED`

### 3.2 Evaluation order

Normative, because it determines which reason a case reports when several apply:

1. role permission → `ROLE_NOT_PERMITTED`
2. claim category declared → `MARKET_VIEW`
3. derivation → `UNTRUSTED_DERIVATION`
4. evidence present → `NO_EVIDENCE`
5. judge registered → `NO_REGISTERED_JUDGE`
6. outcome observed → `OUTCOME_NOT_OBSERVED`
7. party named → `NAMES_A_PARTY`
8. opinion / market view → `OPINION_SHAPED` or `MARKET_VIEW`

Provenance conditions precede lexical ones so a lesson derived from chat is
rejected for **that**, not for happening to contain the word "rise".

### 3.3 Method claim categories (closed set)

Every lesson MUST declare which part of the process it concerns:

`DATA_QUALITY` · `ESTIMATION_METHOD` · `PROCESS_SEQUENCING` ·
`CONSTRAINT_HANDLING` · `RECONCILIATION` · `TIMING_CONVENTION` · `TOOLING`

This is the structural half of "method, not a market view". Lexical detection
leaks by nature; requiring a category means a market call must be filed under a
process step, where the mismatch is visible to the reviewer.

### 3.4 Regime validity

Every lesson records the regime it was learned under, from the calendar in §5. A
lesson from a superseded regime MUST NOT surface without an explicit staleness
flag. Silent staleness is the most likely way this store goes wrong.

**An incomplete calendar MUST report every lesson as possibly superseded.** If
any declared regime has no date, no lesson may be reported as confidently
current — an undated boundary could sit anywhere on the timeline.

## 4. Role scoping

Admission and advice construction are role-scoped.

| Capability | Minimum role |
|---|---|
| read a decision record or surfaced lesson | `viewer` |
| construct generic advice | `editor` |
| construct client-specific advice | `advanced_editor` |
| admit a lesson | `advanced_editor` |
| register a judge, supply a regime date | `admin` |

### 4.1 A load-bearing warning about these role names

The names `viewer` / `editor` / `advanced_editor` / `admin` are taken from
`xge/SECURITY.md` in `ato-energy-platform`. **In that repository they exist only
as a client-side permission catalogue** in `xge/apps/web/src/GridEditorPhase5.jsx`,
which that codebase's own inventory describes as *"a client-side permission
catalogue, not a security boundary"*.

The server-side role vocabulary actually enforced in
`platform/shared/auth/middleware.py` is a **different set**: `platform_admin`,
`dso_operator`, `asset_owner`, `read_only`. The `markets` API carries a bare
`role` string claim with no role vocabulary at all.

**Conformance requirement.** An implementation MUST NOT authorise on a
client-asserted role string. It MUST resolve the capability to a server-side
permission check in its own auth layer, and the role names above are the
contract's vocabulary for *which capability*, not a trusted input. An
implementation that reads `role` from a request body or an unverified header and
compares it to this table is non-conformant.

This mapping is an assumption recorded rather than a fact verified: whether these
four names should govern advisory capabilities at all is a decision for whoever
owns the RBAC model, and it has not been taken.

## 5. Regime calendar

Four regimes are declared: `flow_based` (flow-based capacity calculation
go-live), `mfrr_eam` (mFRR energy activation market), `mtu_15min` (15-minute
market time unit), `intraday_gate_closure` (intraday gate-closure reform).

**No date is known to this contract**, and as of v1.1.0 an implementation MUST
NOT hold one. The "April report" the four regimes were said to come from is not
present in any repository here.

The calendar is **supplied, not baked**: an implementation MUST treat undated
regimes as undated, MUST resolve an instant that could fall inside an undated
regime to `REGIME_UNKNOWN`, and MUST NOT infer a boundary date. Supplying a date
MUST require a cited source.

**A regime module MUST contain no date literal**, and an implementation SHOULD
assert this mechanically — a test that scans the module for one. v1.0.0 permitted
`mtu_15min` = `2025-10-01` as a documented default; that was wrong in kind rather
than in value. A date carried in code is a date someone will trust, and the only
honest posture for a module that cannot cite a source is to hold nothing. With no
calendar configured an implementation surfaces nothing as current: a store that
cannot establish currency does not get to assume it.

A wrong boundary date produces a confident wrong staleness label, which is worse
than an admitted unknown.

## 6. Versioning

No silent online learning. Models and lesson sets are versioned artifacts moving
through **freeze → validate → deploy → monitor → gated re-train**. A deployed
version never mutates in place. Every decision record names the exact model and
code version behind it, so any past decision can be reproduced.

## 7. Audit export

One function reconstructs a decision completely: recommendation, inputs known at
the time, feasibility envelope, model and code versions, outcome, and any lesson
it produced. Deterministic — the same stored record MUST re-render
byte-identically. It MUST contain no market observation, only the snapshot
reference and digest.

## 8. Event-driven wake

Predicates evaluate deterministically over supplied public-feed events. A cadence
tick where nothing matched MUST be distinguishable from a real event and MUST NOT
cost a reasoning turn. A burst throttle and a finite lifetime budget of
self-initiated wakes are required, and both MUST be exposed so an agent cannot
claim responsiveness the system will not deliver.

Every feed MUST carry its licence terms. Public availability is not
redistribution rights.
